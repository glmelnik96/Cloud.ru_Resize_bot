# UI-витрина артефактов + живая библиотека знаний — дизайн

Дата: 2026-08-07. Статус: на ревью. Ветка: `feature/research-loop` (поверх блоков 1–4 синтеза Bannerzila).

## Проблема

Пайплайн после этапа «Язык» думает в разы больше, чем показывает: персона,
kb-матч, зацепки (anchor/desired_outcome), чтения ЦА-судьи, метафорные
обоснования живут в бэкенд-state и provenance.json внутри ZIP. Пользователь
видит 20% рассуждений и не принимает ни одного решения, кроме «принять сет»
и «загрузить hero» — при этом текст на баннер выбирает скоринг, а не человек.
Библиотека знаний (`config/knowledge/`) статична: пополняется только вручную
скриптом, артефакты прогонов в неё не возвращаются никак.

Целевой пользователь UI — маркетолог, не пайплайн-инженер: внутренний жаргон
(anchor, инверсия судьи, kb) переводится на язык пользы, артефакты дозируются.

## Часть 1 — Флоу и экраны

Флоу становится: **Бриф → (1) Кому пишем → (2) Выбор текстов → (3) Картинка → Результат.**
Три остановки вместо двух; каждая — реальная точка решения, влияющая на
пайплайн (display-only остановок нет).

### Бриф

- Новое поле: селект «Продукт» — «определить автоматически» (default) /
  конкретный продукт из библиотеки / «без библиотеки».
- `AdBrief.product_slug: str = "auto"` (`"auto" | <slug> | "none"`).
- `understand_product`: явный slug → берём док без автодетекта; `"none"` →
  KB не подключается; `"auto"` → alias-матч как сейчас. Результат кладётся в
  state: `kb_match: {slug, name} | None` (сейчас живёт только в логах).

### Остановка 1 — «Кому пишем» (новый interrupt-узел `hitl_persona_approve`)

Между `derive_persona` и генерацией текстов.

- Экран: read-only плашка «Опираемся на: <продукт>» (или «работаем только по
  брифу») + структурная карточка персоны: сегмент, возраст, боли, мотивации,
  возражения, стиль общения. Списки — редактируемые чипы (удалить/вписать).
- Правка прямая, без повторного LLM-вызова: resume несёт готовую персону.
- Interrupt-payload: `{kind: "persona_approve", persona, kb_match, session_id}`.
- Decision: `{action: "approve", persona: {…}}` (валидация той же Pydantic-моделью
  `Persona`; пустые списки → 422), `{action: "regenerate"}` (персона не
  понравилась целиком → повторный derive_persona), `cancel`, `timeout` — по
  образцу текстовой паузы, включая парковку и таймауты.

### Остановка 2 — «Выбор текстов» (расширение `hitl_text_approve`)

- Пользователь выбирает **карточку-победителя**; скоринг остаётся только
  сортировкой-подсказкой. «Принять все» заменяется на «Взять эту».
- Decision: `{action: "approve", winner_id}`; `regenerate`/`cancel`/`timeout`
  без изменений.
- Узел при resume переставляет победителя в начало `ranked`. Весь даунстрим
  уже живёт конвенцией «candidates[0] — главный» (метафора `prompts[0]`,
  рендер `candidates[0]`) — ниже по течению изменений нет.
- Карточка (вариант «компакт + разворот»):
  - всегда видны: слоган, текст, CTA, предупреждения линта («Может смутить: …» —
    янтарные чипы, включая чтение судьи «ЦА может прочитать это как …»);
  - под разворотом «Почему такой текст ▾»: Зацепка (anchor), «Читатель должен
    подумать» (desired_outcome), «Почему сработает» (reason).

### Остановка 3 — «Картинка» (метафора + hero, один экран)

Расширение существующей паузы hero.

- Экран показывает задумку картинки победителя по-русски: «Задумка» (метафора),
  «Читатель должен подумать» (intended_inference), «Риск прочтения»
  (anti_reading) + технический промпт под спойлером. Рядом — загрузка hero /
  генерация (как сейчас).
- Новое действие: комментарий по-русски → `{action: "metaphor", comment}` →
  ребро назад в `generate_image_prompt`, режим «перегенерируй метафору только
  победителя с учётом комментария» (1 LLM-вызов, не 12) → повторный interrupt
  с обновлённой задумкой. `upload`/`generate`/`cancel` — без изменений.

### Результат — панель «Как сделан этот баннер»

- Человеческим языком: продукт из библиотеки, кому писали (сегмент), победитель
  с зацепкой, метафора, предупреждения. Данные — из state/provenance, новых
  вычислений нет. ZIP с provenance.json остаётся как есть.
- Кнопка «Отметить: пошёл в кампанию / отклонили» — единственная точка записи
  в слой «опыт» библиотеки (см. часть 2). Без отметки прогон в библиотеку
  НЕ попадает.

## Часть 2 — Библиотека знаний в БД

### Принцип: два слоя с разными правилами записи

1. **Факты** — истина от продуктовой команды. Пишут только люди (админ-раздел
   или импорт .docx-пака). Генерация сюда не пишет никогда.
2. **Опыт** — отмеченные артефакты прогонов per product. Пишутся только по
   явной отметке пользователя на панели результата. Подмешиваются в промпты,
   но никогда — как факты о продукте.

### Схема (обе таблицы в основной БД App3)

- `kb_products`: slug, name, aliases (json), tagline, block1, block2, block3
  (markdown), version (int, растёт при каждой правке), updated_by, updated_at,
  archived (bool). История — append-only версии строк (правка = новая строка
  с version+1; чтение берёт максимальную версию неархивного продукта).
- `kb_runs`: id, product_slug, session_id, created_at, marked_by, outcome
  (`shipped | rejected`), payload (json: слоган, CTA, зацепка, обещание,
  lint_flags, метафора + intended_inference). Payload снимается из provenance
  задачи в момент отметки.
- Сид: одноразовая миграция читает нынешние `config/knowledge/*.md` +
  `index.json` в `kb_products` (version=1). Файлы в репо остаются только как
  сид для чистой инсталляции.
- `scripts/build_knowledge.py` дорастает режимом импорта в БД: «.docx-пак →
  upsert kb_products» для массовых обновлений от продуктовой команды.

### Чтение в пайплайне

- `graph/knowledge.py` меняет источник с файлов на БД, интерфейс `ProductDoc`
  (block(), product_facts, audiences, glossary, find_product) не меняется —
  узлы графа не трогаем. Кэш с инвалидацией по версии таблицы.
- Опыт в промптах — две роли одной выборки (top-5 свежих записей продукта с
  outcome=`shipped`; `rejected` только хранится — в промпты пока не идёт):
  - `generate_message_candidates`: секция «уже выпущено — не повторяй буквально»
    (все записи) + секция «планка качества — так выглядит принятое» (те же
    записи как ориентир тона, с явным запретом копирования);
  - `generate_image_prompt`: «эти образы уже использованы — предложи другой»
    (метафоры из записей).
- Нет отмеченных записей → секции не подмешиваются, промпт как сейчас.

### Роли и админ-раздел

- Роли в БД: таблица `user_roles` (user_id → role: `admin | user`). Назначение
  ролей — в админ-разделе. Bootstrap: первый админ поднимается из env
  (`APP3_BOOTSTRAP_ADMIN=<email>`) при старте, дальше env не нужен.
- Раздел «Библиотека» на сайте:
  - всем: read-only просмотр продуктов (юзер видит, на что опирается генерация)
    и отмеченного опыта;
  - админу: правка имени/алиасов/таглайна + трёх блоков (markdown-поля),
    «добавить продукт», «архивировать», история версий, управление ролями.

## API (новое/изменённое)

- `POST /api/tasks/{uid}/decision/persona` — approve (с правленой персоной) /
  regenerate / cancel.
- `POST /api/tasks/{uid}/decision/text` — получает `winner_id`.
- `POST /api/tasks/{uid}/decision/image` — новое действие `metaphor` + `comment`.
- `POST /api/tasks/{uid}/outcome` — отметка `shipped | rejected` → запись в
  `kb_runs` (идемпотентно: повторная отметка обновляет исход).
- `GET /api/kb/products` (все), `PUT /api/kb/products/{slug}` (админ),
  `POST /api/kb/products` (админ), `GET /api/kb/products/{slug}/history` (админ),
  `GET/PUT /api/admin/roles` (админ).
- Интерфейс задачи (`GET /api/tasks/{uid}`) отдаёт данные для панели
  «Как сделан баннер» и текущей остановки (персона/kb_match/метафора).

## Совместимость и деплой

- В state добавляется `graph_version`. Припаркованная задача со старой версией
  при восстановлении на новой топологии не ломается, а завершается понятной
  ошибкой «пайплайн обновился — перезапустите задачу». Дренаж парковки перед
  деплоем остаётся хорошей практикой.
- provenance.json дорастает полями: `winner_id`, правленая персона,
  `metaphor_comment` (если был), `kb_source: {slug, version}` — паспорт должен
  отражать человеческие решения.

## Тесты (TDD, по узлам)

- hitl_persona_approve: interrupt-payload, approve с правкой (валидация),
  regenerate-петля, timeout/cancel.
- hitl_text_approve: winner_id переставляет ranked, неизвестный id → ошибка.
- Петля метафоры: comment → перегенерация только победителя, обновление
  metaphor_meta, повторный interrupt.
- kb в БД: сид-миграция из md, версии правок, чтение ProductDoc эквивалентно
  файловому (снапшот-сравнение), find_product/glossary на БД.
- Опыт: отметка пишет kb_runs из provenance, идемпотентность; промпт-секции
  подмешиваются при наличии записей и отсутствуют без них.
- Роли: bootstrap-админ, 403 для не-админа на PUT, назначение ролей.
- API-контракты всех новых/изменённых эндпоинтов.

## Вне рамок (осознанно)

- Ручная правка англоязычного промпта картинки (только комментарий-перегенерация;
  спойлер — read-only).
- Отдельная share-страница отчёта (панель результата переиспользуется, если
  когда-нибудь понадобится).
- Запасные карточки-финалисты в ZIP.
- Авто-журнал всех прогонов (запись в опыт — только по явной отметке).
- Webinar-флоу (`/webinar`) не трогаем.

## Реализация — порядок

1. Библиотека в БД (сид, ProductDoc из БД, импортёр) — фундамент, ни на что
   в UI не завязан.
2. Граф: product_slug/kb_match → hitl_persona_approve → winner_id → петля
   метафоры → graph_version.
3. API + UI по остановкам (бриф-селект → персона → карточки → картинка →
   панель результата с отметкой).
4. Роли + админ-раздел «Библиотека».
5. Опыт в промптах (две роли выборки).

## Аддендум 2026-08-08 — правки доступа к библиотеке (от Глеба)

Дополнения к разделу ролей (План 2, этап 4):

1. **Правка библиотеки в UI — админ платформы.** Уже в спеке (роль admin);
   подтверждено.
2. **Гранулярный доступ на правку библиотеки.** Админ через UI может выдать
   право правки библиотеки конкретному пользователю из выбираемого списка
   зарегистрированных. Механика: отдельная способность `kb_editor`
   (колонка/таблица прав), не полный admin. UI: в админ-разделе «Библиотека»
   — список пользователей с чекбоксом «может править библиотеку».
   Проверка прав на PUT карточки: admin ИЛИ kb_editor.
3. **Ограничение типа документов.** На платформе в библиотеке хранятся только
   структурированные карточки продуктов (name, aliases, tagline, блоки 1-3 —
   markdown-текст). Никаких загрузок файлов (PDF/DOCX/картинок) в библиотеку;
   API принимает только текстовые поля с лимитами длины. [Уточнить у Глеба:
   имелись ли в виду будущие типы документов кроме карточек продуктов —
   например, tone-of-voice или брифы.]
4. **E2E-проверка «правка падает в библиотеку ИИ».** Обязательный тест
   Плана 2: PUT карточки → новая строка version+1 → refresh_catalog →
   `graph.knowledge.load_catalog()` отдаёт новую версию → следующий запуск
   understand_product берёт обновлённую карточку (проверка через kb_match.version).
   На уровне графа уже покрыто `test_refresh_catalog_injects_db_snapshot` (Task 2
   Плана 1); в Плане 2 добавляется API-уровень.
